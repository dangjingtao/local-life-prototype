# 本地生活 V0.2 PRD

> V0.2 产品需求与设计基线。V0.1 已完结；本文档描述 V0.2 的增量产品事实、信息架构、Mobile / PC 双端能力、功能映射、中高保真 UI 基线与验收边界。

- Product: 本地生活
- Version target: V0.2
- Status: DESIGN BASELINE
- Date: 2026-08-31
- Base: V0.1 已验收原型
- Related baseline: `docs/product/00-product-brief.md`

## 1. 版本目标

V0.2 不推翻 V0.1 已建立的统一私域中台结构，而是在保留“便利店 / 线上商城 / 智慧抗衰”三大业务语义的前提下，把核心用户动线从“可演示概念”升级为更接近真实产品的交易、履约、预约和运营闭环。

本版重点解决 V0.1 已暴露的问题：

1. 便利店缺少购物车，商品只能单件下单、单件结算。
2. 便利店缺少 3 公里短距配送能力，自提闭环需要进一步完整化。
3. 智慧抗衰检测只有核销概念，缺少预约、二维码核销、报告转化与历史记录闭环。
4. 产品缺少全局搜索。
5. 首页业务入口与底部导航表达重复，首页缺少运营承载能力。
6. PC 后台尚未完整覆盖 V0.2 新增的配送、预约、报告和多渠道商城管理需求。
7. V0.1 视觉以概念验证为主；V0.2 需要升级到中高保真产品型原型，足以判断真实产品的信息层级、商业感、交互质量和跨端一致性。

V0.2 成功意味着：

- Mobile 可以连续演示便利店即时履约、线上商城全国履约、智慧抗衰预约检测三条完整主流程。
- PC 可以支撑对应的门店、订单、配送、预约、核销、报告、渠道和运营管理。
- Mobile 与 PC 不只是页面并存，而是通过统一实体、状态和模拟数据形成可解释的跨端业务闭环。
- UI 达到中高保真：已经像真实可用产品，而不是线框或概念页；同时仍保留快速调整信息架构、交互和业务规则的原型效率。

## 2. 产品结构原则

### 2.1 三大业务语义继续保留

V0.2 继续保留三个明确业务语义：

- 便利店
- 线上商城
- 智慧抗衰

“智慧抗衰”继续作为面向用户的产品语义和展示名称；需求文档中的“AI 检测”属于智慧抗衰业务中的检测能力，不替换“智慧抗衰”这一产品语义。

### 2.2 双履约模式不等于双产品入口

V0.2 的商品交易存在两种顶层履约模式：

- 便利店：以线下门店为履约主体，服务约 3 公里范围，支持到店自提和短距配送。
- 线上商城：面向全国的一件代发 / 快递履约，与线下门店库存和配送隔离。

智慧抗衰不是第三种商品履约方式，而是独立的服务预约 / 检测 / 护理业务域。

因此：

- 商品履约是“便利店 + 线上商城”双模式。
- 产品语义仍是“便利店 + 线上商城 + 智慧抗衰”三大业务域。

### 2.3 统一账号继续作为跨场景基础

V0.1 的统一账号 / 用户 ID 规则继续保留：

- 便利店订单、配送、自提记录关联统一用户。
- 商城订单关联统一用户。
- 智慧抗衰预约、核销、检测报告、套餐和复测记录关联统一用户。
- 会员、积分、优惠券、体验券继续跨业务域保持统一账户语义。

### 2.4 搜索统一，交易与履约隔离

V0.2 建立产品级全局搜索，但不建立全局混合购物车。

- 搜索可以跨便利店、商城、智慧抗衰和活动。
- 搜索结果必须标记所属业务域。
- 不同业务域继续遵守各自的购物车、结算、履约或预约规则。
- 不允许便利店与商城跨域混单，不允许不同便利店跨店混单。

### 2.5 Mobile 与 PC 使用同一业务语义，不强行共享布局

- Mobile 负责消费者侧发现、交易、履约跟踪、预约、报告和权益使用。
- PC 负责门店 / 合作商履约、平台运营、配置、核销、报告管理和数据查看。
- 同一对象在两端使用一致的状态名称和核心字段。
- PC 必须承接 V0.2 新增的关键业务能力，不能只有 Mobile mock。

### 2.6 中高保真 UI 基线

V0.2 从“概念原型”进入“中高保真产品型原型”阶段。

中高保真的定义：

- 页面应具备真实产品所需的完整信息层级、状态、内容密度、视觉节奏和关键交互。
- 核心页面应足以进行产品、UX 和视觉方向评审，而不是依赖口头说明补全体验。
- 商品、门店、活动、预约、报告、订单、权益和后台列表必须使用有业务意义的模拟内容，不使用大面积占位文案代替真实结构。
- 不要求逐像素达到生产上线稿，也不要求在 V0.2 解决最终品牌资产、真实图片版权、真实后端和所有边缘运营配置。
- 不为了“高保真”牺牲原型迭代速度；业务规则仍未确认的部分继续使用可追踪 mock，不伪装成正式规则。

#### 便利店视觉方向

便利店参考成熟便利零售小程序（包括 7-ELEVEN 类产品）的信息组织和即时零售体验，但不复制其品牌视觉。

应强化：

- 当前门店、距离、营业 / 配送能力等门店上下文。
- 高频商品分类、促销、价格、会员价、加购和购物车的高效浏览体验。
- 自提 / 短距配送的即时履约感。
- 商品卡、数量控制、购物车浮层 / 入口、结算明细等成熟零售交互。
- 页面可以热闹、可逛，但不能牺牲 Com Design 的信息清晰度与一致性。

#### 线上商城视觉方向

线上商城需要呈现“靠谱的成熟商城”，而不是把便利店页面换一批商品继续使用。

应强化：

- Storefront / Channel 来源表达。
- 商城首页、品类、推荐、商品详情、规格、优惠、购物车、地址、结算和物流信息的完整度。
- 商品视觉、价格层级、促销信息和购买 CTA 的商业可信度。
- 计划性消费和全国快递的体验，与便利店即时履约形成明显区分。

#### 智慧抗衰视觉方向

智慧抗衰需要比 V0.1 更有科技感、专业感和高端服务感，但不使用空洞的赛博装饰替代信息设计。

应强化：

- 检测项目、预约时段、检测状态和报告数据的结构化表达。
- 报告中的指标、趋势 / 对比、护理建议、专属权益和复测提醒具有可信的数据产品感。
- 科技感主要来自信息组织、数据可视化、精细交互、材质层级和适度动态反馈，而不是大面积霓虹、过度渐变或廉价“AI 蓝光”。
- 继续遵守非医疗边界，视觉专业感不得暗示医疗诊断或未经确认的检测准确度。

#### PC 视觉方向

PC 后台同样进入中高保真，不允许 Mobile 精修而 PC 继续停留在功能占位。

- 店主工作台应突出待处理事项、订单 / 预约效率和门店经营上下文。
- 平台运营中台应具有成熟 SaaS / 运营后台的信息密度和操作层级。
- 数据驾驶舱应提高指标层级、图表和场景对比的设计完成度，但不追求纯展示大屏式视觉表演。
- PC 与 Mobile 共享 Com Design Token、业务状态和品牌基调，但按后台效率独立组织布局。

### 2.7 Mock Data 设计要求

V0.2 的模拟数据是设计和验收的一部分，不只是填充物。

至少需要形成可跨页面、跨端复用的一套数据集：

- 多个便利店门店：地址、距离、营业状态、自提 / 短配能力、商品可售差异。
- 便利店商品：分类、规格、原价、会员价、库存 / 可售状态、促销标签。
- 商城 Storefront / Channel：至少体现不同线上来源的语义。
- 商城商品：品类、规格、价格、优惠、配送 / 包邮信息。
- 多个首页虚拟活动：活动主题、展示位、业务归属、关联商品 / 服务 / 权益。
- 智慧抗衰项目：项目说明、适用门店、可约时段、体验 / 套餐信息。
- 预约：可约、已满、已预约、取消 / 改期、已核销等状态样本。
- 检测报告：至少包含可读的指标数据、护理建议、专属券、套餐和复测提醒；同一用户存在多次报告以支持历史对比。
- 订单：便利店自提、便利店短配、商城快递均有可演示状态。
- 用户、会员、积分、优惠券 / 体验券：与订单、预约和报告保持关联。

模拟数据要求：

- 同一 ID / 人 / 门店 / 订单 / 预约 / 报告在 Mobile 与 PC 中关系一致。
- 文案、金额、时间和状态应接近真实业务，不使用 `Lorem ipsum`、`商品 A`、`用户 001` 等低信息量占位作为核心演示数据。
- 允许为了原型演示构造理想化数据，但必须逻辑自洽，不制造与已确认产品规则冲突的“假事实”。

## 3. Mobile 信息架构

### 3.1 一级信息架构

V0.2 Mobile 采用“稳定业务导航 + 运营首页 + 全局搜索”的结构。

设计基线：

```text
本地生活 Mobile
├─ 首页 Home
├─ 便利店 Convenience
├─ 线上商城 Mall
├─ 智慧抗衰 Smart Care
└─ 我的 My
```

说明：

- 首页不再复制三个业务入口，而是运营内容聚合层。
- 便利店、线上商城、智慧抗衰保持明确一级业务语义。
- “我的”承载统一账号、订单、预约、检测、会员和权益资产。
- 全局搜索是跨业务能力，不归属于商城；可从首页显著进入，并允许在其他一级业务页保留搜索入口。

一级导航的最终视觉形态以原型验收为准，但业务层级按上述结构设计。

### 3.2 首页 Home

首页定位为运营首页，不承担完整业务流程本身。

主要模块：

```text
首页
├─ 全局搜索
├─ Banner / Hero 活动
├─ 多个虚拟活动
├─ 主题专区 / 推荐位
├─ 便利店推荐内容
├─ 商城推荐内容
├─ 智慧抗衰推荐内容
├─ 会员 / 积分 / 券运营内容
└─ 消息 / 活动触达入口（沿用既有能力时）
```

要求：

- 支持同时展示多个虚拟活动，而不是只保留单一活动占位。
- 活动可以关联商品、服务、权益或业务专区。
- 首页内容与底部导航不做同构重复。
- 首页运营位需要有 PC 端对应的配置 / 管理表达。

### 3.3 全局搜索

全局搜索范围至少覆盖：

- 便利店商品。
- 线上商城商品。
- 智慧抗衰项目 / 检测 / 护理套餐。
- 首页及运营活动。

建议结果结构：

```text
搜索结果
├─ 全部
├─ 便利店
├─ 商城
├─ 智慧抗衰
└─ 活动
```

每条结果至少表达：

- 名称。
- 所属业务域。
- 必要的价格 / 权益 / 服务信息。
- 进入下一步所需的履约上下文。

#### 便利店搜索约束

便利店商品与门店库存 / 价格 / 履约能力相关：

- 已有当前门店上下文时，按当前门店展示商品可售状态。
- 无当前门店上下文时，进入便利店商品交易前必须先确定门店。
- 全局搜索不能把便利店商品表现为脱离门店的全局库存。

#### 搜索与交易边界

- 不允许便利店商品与商城商品一起结算。
- 不允许不同便利店商品跨店混单。
- 智慧抗衰服务按预约 / 服务订单规则独立处理。

### 3.4 便利店 Convenience IA

```text
便利店
├─ 当前门店 / 门店切换
├─ 门店首页
│  ├─ 分类
│  ├─ 搜索
│  ├─ 推荐 / 活动
│  └─ 商品列表
├─ 商品详情
├─ 门店独立购物车
├─ 结算
│  ├─ 自提
│  │  └─ 取货时段
│  └─ 短距配送
│     └─ 地址 / 配送范围
└─ 订单
   ├─ 自提订单 / 取货码
   └─ 配送订单 / 配送状态
```

### 3.5 线上商城 Mall IA

线上商城与线下便利店完全隔离，并预留“一端多线上店铺 / 多渠道”扩展能力。

```text
线上商城
├─ 商城聚合首页 / 当前 Storefront
├─ 在线店铺 / 渠道标识
├─ 品类频道
├─ 商城搜索 / 筛选
├─ 商品详情
├─ 商城购物车
├─ 地址
├─ 结算
└─ 订单 / 物流详情
```

V0.2 原型至少要让用户感知商品存在“线上店铺 / 渠道来源”，但不要求一次实现复杂的多店切换产品。

### 3.6 智慧抗衰 Smart Care IA

```text
智慧抗衰
├─ 专区首页
├─ 检测 / 服务项目
│  └─ 项目详情
├─ 体验门店
├─ 日期 / 时段预约
├─ 预约详情
│  ├─ 预约码 / 二维码
│  ├─ 取消
│  └─ 改期
├─ 到店核销 / 检测状态
├─ 检测报告
│  ├─ 检测结果数据
│  ├─ 个性化护理建议
│  ├─ 专属券 / 限时权益
│  ├─ 护理套餐入口
│  └─ 复测提醒
└─ 历史检测 / 报告对比
```

### 3.7 我的 My IA

“我的”作为统一账户和跨业务资产中心。

```text
我的
├─ 用户 / 会员身份
├─ 我的订单
│  ├─ 便利店自提
│  ├─ 便利店配送
│  └─ 商城订单
├─ 我的预约
├─ 我的检测
│  ├─ 历次检测
│  └─ 报告对比
├─ 积分
├─ 优惠券 / 体验券
├─ 地址
└─ 其他既有账号 / 私域入口
```

V0.2 不要求把所有能力都变成新的一级页面；重点是统一入口清晰，并避免订单、预约、检测记录散落在不同业务页面后无法找回。

## 4. 便利店业务

### 4.1 业务定位

便利店承担本地高频即时消费，通过附近门店提供：

- 门店商品浏览与购买。
- 到店自提。
- 约 3 公里短距配送。
- 会员价、积分、优惠券等权益结算。
- 到店核销和私域承接。

### 4.2 先选门店

用户必须先确定便利店门店，再进入门店商品选购流程。

目的：

- 明确库存主体。
- 明确价格和活动适用主体。
- 明确是否支持自提 / 3 公里短距配送。
- 降低下单后无法履约的问题。

### 4.3 门店独立购物车

V0.2 新增便利店购物车。

规则：

- 每个线下门店拥有独立购物车上下文。
- 不同门店商品不得混入同一订单。
- 当前门店购物车只结算当前门店可售商品。
- 自提和短距配送可以共用当前门店购物车，在结算阶段选择履约方式。

设计默认：用户切换门店时，各门店购物车可分别保留；再次进入原门店可继续查看原购物车。该保留策略属于交互设计默认值，最终以 V0.2 原型验收为准。

### 4.4 自提流程

主流程：

`选择门店 → 浏览 / 搜索商品 → 加入购物车 → 结算 → 选择自提 → 选择取货时段 → 支付成功 → 备货 → 待取货 → 出示取货码 → 店员扫码核销 → 已取货 / 已完成`

取货时段要求：

- 结算页选择取货时段。
- 最早可选约 15 分钟后。
- 时段按 15 分钟间隔表达。

结算页一次展示：

- 商品金额。
- 会员价 / 会员优惠。
- 可用优惠券。
- 积分抵扣。
- 配送 / 自提相关费用（如适用）。
- 应付金额及分项明细。

### 4.5 3 公里短距配送

V0.2 必须同时表现外卖式短距配送。

主流程：

`选择门店 → 浏览 / 搜索商品 → 加入购物车 → 结算 → 选择配送 → 确认地址及配送范围 → 支付 → 门店接单 / 备货 → 配送中 → 送达 → 已完成`

原型应体现：

- 门店配送范围概念（约 3 公里）。
- 地址是否在可配送范围内。
- 自提 / 配送两种履约方式切换。
- 配送费或相关费用的结算位置。
- 配送订单状态。

V0.2 只验证产品结构和状态，不要求真实地图、骑手调度或即时配送接口。

## 5. 线上商城业务

### 5.1 业务定位

线上商城承担计划性消费和全国一件代发，与便利店本地库存 / 门店配送完全隔离。

商城流程：

`商城 / 品类频道 → 商品详情 → 加入商城购物车 → 地址 → 结算 → 快递发货 → 物流跟踪 → 签收`

### 5.2 履约隔离

- 商城订单不依赖线下便利店。
- 商城商品不进入便利店购物车。
- 商城结算不出现便利店自提 / 3 公里短配规则。
- 商城可以表达全国包邮、满额包邮等快递规则。

### 5.3 一端多店 / 多渠道扩展

线上商城未来可能以“一端多线上店铺 / 多渠道”的形态存在，例如自营商城、外部平台店铺等。

因此 V0.2 的产品和数据结构不得把线上商城写死为唯一单店模型。

需要预留以下语义：

- Storefront / 在线店铺。
- Channel / 渠道。
- 商品与店铺 / 渠道关系。
- 订单来源渠道。

抖音店等仅作为未来可能渠道示例；V0.2 不要求真实接入抖音接口，不宣称已实现外部平台数据同步。

## 6. 智慧抗衰

### 6.1 业务定位

智慧抗衰继续作为明确业务语义展示。

V0.2 将其从 V0.1 的“体验券 + 核销 + 基础报告”升级为完整的预约检测与后续转化闭环。

### 6.2 主流程

`进入智慧抗衰 → 选择检测 / 服务项目 → 选择体验门店 → 选择日期 / 时段 → 确认预约 → 生成预约码 → 到店亮码 → 店员扫码核销 → 完成检测 / 体验 → 报告推送 → 查看报告 → 护理建议 / 专属券 / 套餐转化 → 复测提醒`

### 6.3 预约规则

预约能力按“门店 × 项目 × 日期”维护可预约时段。

原型需表现：

- 可预约日期。
- 可预约时段。
- 已满 / 不可约状态。
- 预约详情。
- 预约码 / 二维码。
- 取消预约。
- 改期。

取消 / 改期规则：开始前 2 小时可操作。

### 6.4 双向码核销

V0.2 不再只展示文字核销码。

必须体现：

- 用户端展示预约二维码 / 预约码。
- 店员端支持扫码核销。
- 核销前 / 核销中 / 核销成功状态。
- 核销结果与当前用户、门店、项目、预约记录关联。

### 6.5 检测报告升级

V0.2 报告页必须包含：

- 检测结果数据。
- 个性化护理建议。
- 专属优惠券 / 限时权益。
- 护理套餐购买入口。
- 复测提醒。

报告仍继承 V0.1 的安全边界：作为原型中的消费服务 / 护理建议，不包装为医疗诊断，不承诺高精度、全面、实时或医疗性质判断。

### 6.6 历史检测与报告对比

“我的”中增加“我的检测”能力：

- 展示历次检测记录。
- 可进入每次报告详情。
- 支持历史报告对比表达。
- 显示检测日期、门店、项目等基础上下文。

V0.2 只要求原型表达对比结构，不要求真实 AI 趋势分析算法。

## 7. 会员、积分与权益

V0.1 的统一会员、积分、优惠券、体验券体系继续保留。

V0.2 重点要求在真实动线中使用这些权益，而不仅作为会员中心静态展示：

- 便利店结算页统一计算会员价、优惠券、积分抵扣。
- 智慧抗衰报告页可发放 / 展示专属券。
- 检测完成后可承接护理套餐或后续权益。
- 活动首页可以承载会员和权益运营活动。

积分比例、会员等级倍率、有效期、成本承担等未被本轮需求重新确认，继续保持待确认，不在 V0.2 PRD 中擅自固定。

## 9. 核心实体与关系

V0.2 原型至少应保持以下数据语义稳定。

### User

统一用户 ID，关联会员、积分、券、便利店订单、商城订单、预约和报告。

### Offline Store

线下履约门店，关联：

- 地址。
- 商品可售范围。
- 自提能力。
- 3 公里短距配送能力。
- 智慧抗衰服务项目。
- 可预约时段。

### Convenience Cart

门店独立购物车；必须关联某一个 Offline Store。

### Online Storefront / Channel

线上商城的店铺 / 渠道语义，与 Offline Store 分离。

### Order

订单至少需要区分来源和履约域：

- convenience-pickup
- convenience-delivery
- mall-shipping
- care-service / care-package（如原型形成服务订单）

### Appointment

关联：

- User
- Offline Store
- Care Project
- Date / Time Slot
- Appointment Code / QR
- Status

### Detection Report

关联：

- User
- Appointment / Detection Record
- Offline Store
- Care Project
- Result
- Advice
- Benefit / Coupon
- Package CTA
- Retest Reminder

### Campaign / Activity

首页运营活动，至少可以关联：

- 展示位。
- 业务域。
- 商品 / 服务 / 权益。
- 跳转目标。

## 12. 明确不在 V0.2 实现范围

除非后续单独确认，V0.2 仍不建设：

- 正式生产后端。
- 真实支付系统。
- 真实库存系统。
- 真实骑手调度 / 即时配送平台接口。
- 真实物流接口。
- 抖音等外部商城真实 API 接入。
- 真实检测硬件接入。
- 医疗诊断能力。
- 真实 AI 检测算法。
- 真实 AI 护理建议生成。
- 生产级数据仓库 / 实时 BI。
- 生产级 CMS / 搜索索引系统。
- 最终生产级品牌视觉和逐像素上线稿。

V0.2 可以使用一致的模拟数据、状态和交互来验证完整产品结构，但 UI 必须达到中高保真产品型原型要求。

## 13. V0.2 验收标准

### AC-V02-001 产品语义

便利店、线上商城、智慧抗衰三大业务语义均被明确保留；智慧抗衰不被“AI 检测”名称替代。

### AC-V02-002 首页与导航

Mobile 具有稳定的业务 IA；首页能够承载多个虚拟活动和运营内容，不再只是复制业务导航入口。

### AC-V02-003 全局搜索

存在产品级搜索，可覆盖便利店商品、商城商品、智慧抗衰项目 / 套餐和活动；结果明确业务归属。

### AC-V02-004 便利店购物车

便利店支持门店独立购物车，同一订单不跨门店混单。

### AC-V02-005 便利店自提

可以连续演示：选店 → 加购 → 结算 → 自提时段 → 备货 → 取货码 → 店员核销 → 完成。

### AC-V02-006 便利店短距配送

可以连续演示约 3 公里短距配送流程，并表现地址配送范围、配送订单及关键状态。

### AC-V02-007 结算权益

便利店结算页能够同时表达会员价、优惠券、积分抵扣和金额分项。

### AC-V02-008 商城履约隔离

商城使用独立购物车和全国快递流程，不与便利店库存、购物车、自提或短距配送混单。

### AC-V02-009 商城多店 / 多渠道语义

产品与后台结构能够表达线上 Storefront / Channel，不把线上商城锁死成唯一单店；无需真实外部平台接入。

### AC-V02-010 智慧抗衰预约

可以连续演示：项目 → 门店 → 日期 / 时段 → 预约码 → 店员扫码核销 → 检测 → 报告。

### AC-V02-011 预约管理

PC 可表达按门店 × 项目 × 日期维护可约时段，并能查看预约、取消 / 改期和核销状态。

### AC-V02-012 报告转化

报告页包含检测结果数据、个性化护理建议、专属券、护理套餐入口和复测提醒。

### AC-V02-013 历史检测

“我的检测”可以查看历次报告，并存在历史报告对比表达。

### AC-V02-014 PC 双端支撑

PC 后台能够支撑便利店自提 / 短配、智慧抗衰预约 / 核销 / 报告、线上商城渠道结构及首页活动运营，而非仅有 Mobile mock。

### AC-V02-015 跨端功能映射

PRD 中定义的关键 Mobile 功能存在对应 PC 承接或明确说明不需要后台承接；施工后不得出现关键业务只在单端存在、无法解释后台来源的情况。

### AC-V02-016 数据一致性

同一用户、订单、预约、核销和报告在 Mobile 与 PC 的模拟数据关系保持一致。

### AC-V02-017 原型质量

V0.1 已建立的关键状态、可访问性、移动端触控目标、PC / Mobile 响应式质量要求继续有效，并覆盖 V0.2 新页面。

### AC-V02-018 中高保真 UI

Mobile 与 PC 核心页面达到中高保真产品型原型标准：信息完整、视觉层级清晰、真实内容密度合理、关键交互可判断；不能继续以线框、占位卡片或单纯“能点”为完成标准。

三个业务域应有明确体验区分：

- 便利店体现成熟便利零售和即时履约感。
- 线上商城体现成熟电商和全国履约感。
- 智慧抗衰体现科技、专业、高端服务与数据产品感。

### AC-V02-019 Mock Data

V0.2 使用成体系的模拟数据支持核心演示；便利店、商城、活动、预约、报告、订单、会员 / 权益均存在可读样本，并且关键实体在 Mobile / PC 之间保持一致关系。

## 14. 当前未决事项

以下事项尚未被本轮 V0.2 需求确认，不得自行固化为正式业务规则：

1. 3 公里配送的精确距离计算、配送费、起送价、配送主体和预计时长。
2. 门店切换时不同门店购物车的最终清理 / 保留策略；V0.2 原型默认按“各店独立保留”设计，待验收确认。
3. 商城在线店铺 / 渠道的正式层级和未来抖音等外部平台的真实数据打通范围。
4. 会员等级、积分比例、有效期和权益成本承担机制。
5. 智慧抗衰检测设备、真实字段和真实算法能力。
6. 个性化护理建议在生产系统中的生成机制。
7. 专属券、护理套餐和复测提醒的真实营销规则。
8. 支付、退款、分账、结算和售后责任主体。
9. 数据驾驶舱新增指标的正式统计口径。
10. Mobile 一级导航最终视觉形态；V0.2 业务 IA 已确定按 Home / Convenience / Mall / Smart Care / My 组织，视觉呈现以原型评审为准。
11. 最终品牌视觉资产、商品图片版权和生产级素材规范；V0.2 只要求中高保真产品体验，不以最终上线视觉稿为交付边界。

这些未决事项不阻塞 V0.2 中高保真原型设计；原型应使用可追踪的 mock / 说明表达，不包装为已确定生产规则。
