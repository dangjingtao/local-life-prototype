# 本地生活 V0.2 PRD

> V0.2 产品需求与设计基线。V0.1 已完结；本文档描述 V0.2 的增量产品事实、信息架构、Mobile / PC 双端能力与验收边界。

- Product: 本地生活
- Version target: V0.2
- Status: DESIGN BASELINE
- Date: 2026-08-31
- Base: V0.1 已验收原型
- Related baseline: `docs/product/00-product-brief.md`

---

## 1. 版本目标

V0.2 不推翻 V0.1 已建立的统一私域中台结构，而是在保留“便利店 / 线上商城 / 智慧抗衰”三大业务语义的前提下，把核心用户动线从“可演示概念”升级为更接近真实产品的交易、履约、预约和运营闭环。

本版重点解决 V0.1 已暴露的问题：

1. 便利店缺少购物车，商品只能单件下单、单件结算。
2. 便利店缺少 3 公里短距配送能力，自提闭环需要进一步完整化。
3. 智慧抗衰检测只有核销概念，缺少预约、二维码核销、报告转化与历史记录闭环。
4. 产品缺少全局搜索。
5. 首页业务入口与底部导航表达重复，首页缺少运营承载能力。
6. PC 后台尚未完整覆盖 V0.2 新增的配送、预约、报告和多渠道商城管理需求。

V0.2 成功意味着：Mobile 可以连续演示便利店即时履约、线上商城全国履约、智慧抗衰预约检测三条完整主流程；PC 可以支撑对应的门店、订单、配送、预约、核销、报告、渠道和运营管理。

## 2. 产品结构原则

### 2.1 三大业务语义继续保留

V0.2 继续保留三个明确业务语义：

- 便利店
- 线上商城
- 智慧抗衰

“智慧抗衰”继续作为面向用户的产品语义和展示名称；需求文档中的“AI 检测”属于智慧抗衰业务中的检测能力，不替换“智慧抗衰”这一产品语义。

### 2.2 双履约模式不等于双产品入口

V0.2 的商品交易存在两种顶层履约模式：

- 便利店：以线下门店为履约主体，服务约 3 公里范围，支持到店自提和短距配送。
- 线上商城：面向全国的一件代发 / 快递履约，与线下门店库存和配送隔离。

智慧抗衰不是第三种商品履约方式，而是独立的服务预约 / 检测 / 护理业务域。

因此：

- 商品履约是“便利店 + 线上商城”双模式。
- 产品语义仍是“便利店 + 线上商城 + 智慧抗衰”三大业务域。

### 2.3 统一账号继续作为跨场景基础

V0.1 的统一账号 / 用户 ID 规则继续保留：

- 便利店订单、配送、自提记录关联统一用户。
- 商城订单关联统一用户。
- 智慧抗衰预约、核销、检测报告、套餐和复测记录关联统一用户。
- 会员、积分、优惠券、体验券继续跨业务域保持统一账户语义。

## 3. Mobile 信息架构

### 3.1 首页职责调整

首页不再简单复制底部导航的三个业务入口。

V0.2 首页定位为“运营首页”，承担：

- 多个虚拟活动展示。
- Banner / 主题活动 / 推荐内容。
- 业务推荐入口。
- 商品、服务、会员权益等运营内容承接。
- 全局搜索入口。

底部导航承担稳定的信息架构；首页承担运营和内容编排。二者不再做同构重复。

### 3.2 全局搜索

V0.2 增加产品级全局搜索，不限定在商城模块内部。

搜索范围至少覆盖：

- 便利店商品。
- 线上商城商品。
- 智慧抗衰项目 / 检测 / 护理套餐。
- 首页及运营活动。

搜索结果必须明确所属业务域，并遵守所属业务域的交易或预约规则。

#### 便利店搜索约束

便利店商品与门店库存 / 价格 / 履约能力相关：

- 已有当前门店上下文时，按当前门店展示商品可售状态。
- 无当前门店上下文时，进入便利店商品交易前必须先确定门店。
- 全局搜索不能把便利店商品表现为脱离门店的全局库存。

#### 搜索与交易边界

搜索可以统一，但交易不能混单：

- 不允许便利店商品与商城商品一起结算。
- 不允许不同便利店的商品跨店混单。
- 智慧抗衰服务按预约 / 服务订单规则独立处理。

## 4. 便利店业务

### 4.1 业务定位

便利店承担本地高频即时消费，通过附近门店提供：

- 门店商品浏览与购买。
- 到店自提。
- 约 3 公里短距配送。
- 会员价、积分、优惠券等权益结算。
- 到店核销和私域承接。

### 4.2 先选门店

用户必须先确定便利店门店，再进入门店商品选购流程。

目的：

- 明确库存主体。
- 明确价格和活动适用主体。
- 明确是否支持自提 / 3 公里短距配送。
- 降低下单后无法履约的问题。

### 4.3 门店独立购物车

V0.2 新增便利店购物车。

规则：

- 每个线下门店拥有独立购物车上下文。
- 不同门店商品不得混入同一订单。
- 当前门店购物车只结算当前门店可售商品。
- 自提和短距配送可以共用当前门店购物车，在结算阶段选择履约方式。

设计默认：用户切换门店时，各门店购物车可分别保留；再次进入原门店可继续查看原购物车。该保留策略属于交互设计默认值，最终以 V0.2 原型验收为准。

### 4.4 自提流程

主流程：

`选择门店 → 浏览 / 搜索商品 → 加入购物车 → 结算 → 选择自提 → 选择取货时段 → 支付成功 → 备货 → 待取货 → 出示取货码 → 店员扫码核销 → 已取货 / 已完成`

取货时段要求：

- 结算页选择取货时段。
- 最早可选约 15 分钟后。
- 时段按 15 分钟间隔表达。

结算页一次展示：

- 商品金额。
- 会员价 / 会员优惠。
- 可用优惠券。
- 积分抵扣。
- 配送 / 自提相关费用（如适用）。
- 应付金额及分项明细。

### 4.5 3 公里短距配送

V0.2 必须同时表现外卖式短距配送。

主流程：

`选择门店 → 浏览 / 搜索商品 → 加入购物车 → 结算 → 选择配送 → 确认地址及配送范围 → 支付 → 门店接单 / 备货 → 配送中 → 送达 → 已完成`

原型应体现：

- 门店配送范围概念（约 3 公里）。
- 地址是否在可配送范围内。
- 自提 / 配送两种履约方式切换。
- 配送费或相关费用的结算位置。
- 配送订单状态。

V0.2 只验证产品结构和状态，不要求真实地图、骑手调度或即时配送接口。

## 5. 线上商城业务

### 5.1 业务定位

线上商城承担计划性消费和全国一件代发，与便利店本地库存 / 门店配送完全隔离。

商城流程：

`商城 / 品类频道 → 商品详情 → 加入商城购物车 → 地址 → 结算 → 快递发货 → 物流跟踪 → 签收`

### 5.2 履约隔离

- 商城订单不依赖线下便利店。
- 商城商品不进入便利店购物车。
- 商城结算不出现便利店自提 / 3 公里短配规则。
- 商城可以表达全国包邮、满额包邮等快递规则。

### 5.3 一端多店 / 多渠道扩展

线上商城未来可能以“一端多线上店铺 / 多渠道”的形态存在，例如自营商城、外部平台店铺等。

因此 V0.2 的产品和数据结构不得把线上商城写死为唯一单店模型。

需要预留以下语义：

- Storefront / 在线店铺。
- Channel / 渠道。
- 商品与店铺 / 渠道关系。
- 订单来源渠道。

抖音店等仅作为未来可能渠道示例；V0.2 不要求真实接入抖音接口，不宣称已实现外部平台数据同步。

## 6. 智慧抗衰

### 6.1 业务定位

智慧抗衰继续作为明确业务语义展示。

V0.2 将其从 V0.1 的“体验券 + 核销 + 基础报告”升级为完整的预约检测与后续转化闭环。

### 6.2 主流程

`进入智慧抗衰 → 选择检测 / 服务项目 → 选择体验门店 → 选择日期 / 时段 → 确认预约 → 生成预约码 → 到店亮码 → 店员扫码核销 → 完成检测 / 体验 → 报告推送 → 查看报告 → 护理建议 / 专属券 / 套餐转化 → 复测提醒`

### 6.3 预约规则

预约能力按“门店 × 项目 × 日期”维护可预约时段。

原型需表现：

- 可预约日期。
- 可预约时段。
- 已满 / 不可约状态。
- 预约详情。
- 预约码 / 二维码。
- 取消预约。
- 改期。

取消 / 改期规则：开始前 2 小时可操作。

### 6.4 双向码核销

V0.2 不再只展示文字核销码。

必须体现：

- 用户端展示预约二维码 / 预约码。
- 店员端支持扫码核销。
- 核销前 / 核销中 / 核销成功状态。
- 核销结果与当前用户、门店、项目、预约记录关联。

### 6.5 检测报告升级

V0.2 报告页必须包含：

- 检测结果数据。
- 个性化护理建议。
- 专属优惠券 / 限时权益。
- 护理套餐购买入口。
- 复测提醒。

报告仍继承 V0.1 的安全边界：作为原型中的消费服务 / 护理建议，不包装为医疗诊断，不承诺高精度、全面、实时或医疗性质判断。

### 6.6 历史检测与报告对比

“我的”中增加“我的检测”能力：

- 展示历次检测记录。
- 可进入每次报告详情。
- 支持历史报告对比表达。
- 显示检测日期、门店、项目等基础上下文。

V0.2 只要求原型表达对比结构，不要求真实 AI 趋势分析算法。

## 7. 会员、积分与权益

V0.1 的统一会员、积分、优惠券、体验券体系继续保留。

V0.2 重点要求在真实动线中使用这些权益，而不仅作为会员中心静态展示：

- 便利店结算页统一计算会员价、优惠券、积分抵扣。
- 智慧抗衰报告页可发放 / 展示专属券。
- 检测完成后可承接护理套餐或后续权益。
- 活动首页可以承载会员和权益运营活动。

积分比例、会员等级倍率、有效期、成本承担等未被本轮需求重新确认，继续保持待确认，不在 V0.2 PRD 中擅自固定。

## 8. PC 后台

V0.2 的设计必须包含 PC 后台支持。Mobile 新增能力不能只通过前端 mock 孤立存在。

### 8.1 店主 / 合作商工作台

#### 便利店订单与履约

- 今日订单 / 待处理订单。
- 自提订单。
- 待备货 / 待取货状态。
- 取货码扫码核销。
- 3 公里配送订单。
- 配送中 / 已送达等状态。
- 当前门店范围内的订单和用户概览。

#### 智慧抗衰预约

- 预约列表。
- 按项目 / 日期查看预约。
- 预约详情。
- 预约二维码扫码核销。
- 取消 / 改期状态查看。
- 今日待检测 / 已完成记录。

#### 可约时段管理

店主 / 授权人员需要能够维护：

- 门店。
- 智慧抗衰项目。
- 日期。
- 可约时段。
- 不可约 / 已满状态。

### 8.2 平台运营中台

V0.2 在 V0.1 运营中台基础上补充以下模块或能力：

#### 便利店运营

- 门店履约方式配置概念：自提 / 短距配送。
- 配送范围概念。
- 门店商品 / 库存可售状态表达。
- 自提订单与配送订单区分。

#### 线上商城 / 渠道

- 在线店铺 / Storefront 管理结构。
- 渠道 / Channel 管理结构。
- 商品与线上店铺 / 渠道关系。
- 订单来源渠道。

V0.2 不做真实外部平台接口，但后台结构应避免把商城写死为唯一单店。

#### 智慧抗衰

- 检测 / 服务项目管理。
- 适用门店管理。
- 预约时段管理。
- 预约订单管理。
- 核销记录。
- 检测记录。
- 报告查看 / 管理结构。
- 报告后专属券 / 套餐 / 复测提醒的运营配置结构。

#### 活动与搜索运营

- 首页虚拟活动配置概念。
- 活动展示位 / 推荐位概念。
- 全局搜索结果应可以关联商品、服务和活动实体。

### 8.3 数据驾驶舱

继续保留 V0.1 驾驶舱，并在 V0.2 数据表达中补充可区分：

- 便利店自提订单。
- 便利店短距配送订单。
- 线上商城订单。
- 智慧抗衰预约量。
- 智慧抗衰核销量 / 完成量。
- 检测后套餐 / 权益转化概念。

V0.2 仍使用模拟数据，不要求真实指标平台。

## 9. 核心实体与关系

V0.2 原型至少应保持以下数据语义稳定：

### User

统一用户 ID，关联会员、积分、券、便利店订单、商城订单、预约和报告。

### Offline Store

线下履约门店，关联：

- 地址。
- 商品可售范围。
- 自提能力。
- 3 公里短距配送能力。
- 智慧抗衰服务项目。
- 可预约时段。

### Convenience Cart

门店独立购物车；必须关联某一个 Offline Store。

### Online Storefront / Channel

线上商城的店铺 / 渠道语义，与 Offline Store 分离。

### Order

订单至少需要区分来源和履约域：

- convenience-pickup
- convenience-delivery
- mall-shipping
- care-service / care-package（如原型形成服务订单）

### Appointment

关联：

- User
- Offline Store
- Care Project
- Date / Time Slot
- Appointment Code / QR
- Status

### Detection Report

关联：

- User
- Appointment / Detection Record
- Offline Store
- Care Project
- Result
- Advice
- Benefit / Coupon
- Package CTA
- Retest Reminder

## 12. 明确不在 V0.2 实现范围

除非后续单独确认，V0.2 仍不建设：

- 正式生产后端。
- 真实支付系统。
- 真实库存系统。
- 真实骑手调度 / 即时配送平台接口。
- 真实物流接口。
- 抖音等外部商城真实 API 接入。
- 真实检测硬件接入。
- 医疗诊断能力。
- 真实 AI 检测算法。
- 真实 AI 护理建议生成。

## 13. V0.2 验收标准

### AC-V02-001 产品语义

便利店、线上商城、智慧抗衰三大业务语义均被明确保留；智慧抗衰不被“AI 检测”名称替代。

### AC-V02-002 首页与导航

首页能够承载多个虚拟活动和运营内容，不再只是复制底部导航入口。

### AC-V02-003 全局搜索

存在产品级搜索，可覆盖便利店商品、商城商品、智慧抗衰项目 / 套餐和活动；结果明确业务归属。

### AC-V02-004 便利店购物车

便利店支持门店独立购物车，同一订单不跨门店混单。

### AC-V02-005 便利店自提

可以连续演示：选店 → 加购 → 结算 → 自提时段 → 备货 → 取货码 → 店员核销 → 完成。

### AC-V02-006 便利店短距配送

可以连续演示约 3 公里短距配送流程，并表现地址配送范围、配送订单及关键状态。

### AC-V02-007 结算权益

便利店结算页能够同时表达会员价、优惠券、积分抵扣和金额分项。

### AC-V02-008 商城履约隔离

商城使用独立购物车和全国快递流程，不与便利店库存、购物车、自提或短距配送混单。

### AC-V02-009 商城多店 / 多渠道语义

产品与后台结构能够表达线上 Storefront / Channel，不把线上商城锁死成唯一单店；无需真实外部平台接入。

### AC-V02-010 智慧抗衰预约

可以连续演示：项目 → 门店 → 日期 / 时段 → 预约码 → 店员扫码核销 → 检测 → 报告。

### AC-V02-011 预约管理

PC 可表达按门店 × 项目 × 日期维护可约时段，并能查看预约、取消 / 改期和核销状态。

### AC-V02-012 报告转化

报告页包含检测结果数据、个性化护理建议、专属券、护理套餐入口和复测提醒。

### AC-V02-013 历史检测

“我的检测”可以查看历次报告，并存在历史报告对比表达。

### AC-V02-014 PC 双端支撑

PC 后台能够支撑便利店自提 / 短配、智慧抗衰预约 / 核销 / 报告、线上商城渠道结构及首页活动运营，而非仅有 Mobile mock。

### AC-V02-015 数据一致性

同一用户、订单、预约、核销和报告在 Mobile 与 PC 的模拟数据关系保持一致。

### AC-V02-016 原型质量

V0.1 已建立的关键状态、可访问性、移动端触控目标、PC / Mobile 响应式质量要求继续有效，并覆盖 V0.2 新页面。

## 14. 当前未决事项

以下事项尚未被本轮 V0.2 需求确认，不得自行固化为正式业务规则：

1. 3 公里配送的精确距离计算、配送费、起送价、配送主体和预计时长。
2. 门店切换时不同门店购物车的最终清理 / 保留策略；V0.2 原型默认按“各店独立保留”设计，待验收确认。
3. 商城在线店铺 / 渠道的正式层级和未来抖音等外部平台的真实数据打通范围。
4. 会员等级、积分比例、有效期和权益成本承担机制。
5. 智慧抗衰检测设备、真实字段和真实算法能力。
6. 个性化护理建议在生产系统中的生成机制。
7. 专属券、护理套餐和复测提醒的真实营销规则。
8. 支付、退款、分账、结算和售后责任主体。
9. 数据驾驶舱新增指标的正式统计口径。

这些未决事项不阻塞 V0.2 概念原型设计；原型应使用可追踪的 mock / 说明表达，不包装为已确定生产规则。
